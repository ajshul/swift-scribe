# Notion Sync Integration

## Configuration

### User Setup (In-App)

Users connect to Notion via OAuth - no manual token copying required:

1. **Connect to Notion**:
   - Go to Settings → Notion Integration
   - Tap "Connect to Notion"
   - Sign in to Notion in the browser
   - Authorize Swift Scribe
   - Select pages/databases to share with the app

2. **Select a Database**:
   - After connecting, tap "Select Database"
   - Choose a database from the list of shared databases
   - The database should have a "Name" title property (standard)

3. **Optional Settings**:
   - Enable "Auto-sync after recording" to sync automatically
   - Use "Test Connection" to verify everything works

### Developer Setup (OAuth App)

To enable OAuth login, you need to create a Notion public integration:

1. **Create Public Integration**:
   - Go to https://www.notion.so/my-integrations
   - Click "New integration"
   - Name it (e.g., "Swift Scribe")
   - Select **"Public"** integration type
   - Set redirect URI: `swiftscribe://notion-callback`

2. **Configure OAuth Credentials**:
   - Copy the **OAuth client ID** and **OAuth client secret**
   - Update `NotionOAuthService.swift`:
     ```swift
     private let clientId = "YOUR_CLIENT_ID"
     private let clientSecret = "YOUR_CLIENT_SECRET"
     ```

3. **URL Scheme**:
   - The app's `Info.plist` registers the `swiftscribe://` URL scheme
   - Notion redirects back to `swiftscribe://notion-callback` after authorization

### OAuth Flow

```
User taps "Connect to Notion"
  -> ASWebAuthenticationSession opens Notion OAuth page
  -> User logs in and authorizes app
  -> User selects which pages/databases to share
  -> Notion redirects to swiftscribe://notion-callback?code=...
  -> App exchanges code for access token (POST /v1/oauth/token)
  -> Token stored securely in Keychain
  -> App fetches available databases (POST /v1/search)
  -> User selects target database
  -> Configuration complete
```

## API Details

### Notion-Version Header

```
Notion-Version: 2022-06-28
```

We use `2022-06-28` (stable, widely supported) rather than `2025-09-03` which introduces breaking changes (`data_source_id` replacing `database_id`). The `2022-06-28` version is well-documented and reliable. This value is centralized in `NotionService.notionVersion`.

**When to update**: If Notion deprecates `2022-06-28` or new features are needed, update `NotionService.notionVersion` and adjust the parent field to use `data_source_id` per the 2025-09-03 migration guide.

### Required Headers (All Requests)

```
Authorization: Bearer <integration_token>
Content-Type: application/json
Notion-Version: 2022-06-28
```

### Create Page

**Endpoint:** `POST https://api.notion.com/v1/pages`

**Request body:**

```json
{
  "parent": {
    "database_id": "<database_id>"
  },
  "icon": { "type": "emoji", "emoji": "🎙️" },
  "properties": {
    "Name": {
      "title": [{ "type": "text", "text": { "content": "Meeting Title" } }]
    },
    "Date": {
      "date": { "start": "2026-01-29T10:00:00.000Z" }
    }
  },
  "children": [
    // First batch of blocks (max 100)
  ]
}
```

**Notes:**
- The `Date` property is set only if the database has a matching Date property; if the API returns a validation error for it, we silently retry without it.
- Properties like `Title` use the property name as it appears in the database. We default to "Name" but this is configurable.

### Append Block Children

**Endpoint:** `PATCH https://api.notion.com/v1/blocks/{page_id}/children`

Used for:
- Adding more blocks when >100 blocks needed
- Updating an existing page with new content

```json
{
  "children": [
    {
      "object": "block",
      "type": "paragraph",
      "paragraph": {
        "rich_text": [{ "type": "text", "text": { "content": "..." } }]
      }
    }
  ]
}
```

### Page Content Structure

When creating a meeting notes page, we use this block structure:

```
Heading 2: "Summary"
Paragraph: <summary text>

Heading 2: "Decisions"
Bulleted list items: <each decision>
  (or Paragraph: "None" if empty)

Heading 2: "Action Items"
To-do blocks: <each action item> (checked: false)
  (or Paragraph: "None" if empty)

Toggle: "Transcript"
  Paragraph children: <transcript text, chunked into 2000-char segments>

Paragraph: "Generated by Swift Scribe • <date>"
```

### Content Chunking

Notion has these limits:
- Rich text content: **2,000 characters** per text element
- Rich text array: **100 elements** max
- Children array: **100 blocks** max per request
- Total payload: **500 KB** max

For long transcripts:
1. Split text into 2,000-character segments at word boundaries
2. Each segment becomes one `rich_text` element in a paragraph block
3. If >100 paragraph blocks needed, use multiple `PATCH .../children` calls
4. Transcript paragraphs are nested inside a toggle block

### Update Strategy

When a page already has a `notionPageId`:
- We **append** new content rather than replacing
- A divider + heading "Updated <date>" is prepended to new content
- This preserves the original notes and shows the update history

## File Upload / Audio Attachment

### Strategy

The Notion API supports file uploads via `POST /v1/file_uploads`:

1. Create upload object: `POST /v1/file_uploads`
2. Send file data: `POST /v1/file_uploads/{id}/send` (multipart/form-data)
3. Reference in audio block: `{ "type": "file_upload", "file_upload": { "id": "..." } }`

### Constraints

| Workspace | Max File Size |
|-----------|--------------|
| Free | 5 MiB |
| Paid | 5 GiB |

### Implementation

- Audio is recorded in AAC (.m4a) format at a practical bitrate to keep files small
- Before upload, check file size against 5 MiB limit (conservative, works for all plans)
- If file <= 5 MiB: upload and attach as audio block
- If file > 5 MiB: skip upload, add paragraph "Audio file too large to attach (>5 MiB)"
- Upload must be attached within 1 hour of creation or it expires

### Audio Block Format

```json
{
  "type": "audio",
  "audio": {
    "type": "file_upload",
    "file_upload": { "id": "<file_upload_id>" }
  }
}
```

## Error Handling

| HTTP Status | Code | User Message | Action |
|-------------|------|-------------|--------|
| 401 | `unauthorized` | "Notion token is invalid" | Prompt to re-enter token |
| 403 | `restricted_resource` | "Integration doesn't have access to this database" | Prompt to share DB |
| 404 | `object_not_found` | "Database not found or not shared with integration" | Check DB ID + sharing |
| 409 | `conflict_error` | "Sync conflict, retrying..." | Auto-retry |
| 429 | `rate_limited` | "Rate limited, retrying..." | Wait `Retry-After` seconds |
| 5xx | various | "Notion server error, will retry" | Auto-retry with backoff |

## Retry Queue

- Failed syncs are queued with `syncState = .failed(errorMessage)`
- Retry logic: exponential backoff (2s, 4s, 8s, 16s, max 60s)
- Max 5 retry attempts per sync
- Queue persists in SwiftData (survives app restart)
- Auto-sync (if enabled) triggers after summarization completes
- Manual retry available via "Sync to Notion" button

## Rate Limiting

- Notion allows ~3 requests/second per integration
- We throttle to 1 request per 500ms for safety
- Batch operations (multiple append calls) respect this limit
- 429 responses are handled by reading `Retry-After` header
